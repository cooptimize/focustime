# FocusTime

Local, visual week-planning and focus app for Tanner on Omarchy. A week grid of half-day focus blocks with meetings and personal events layered on, risk flags, and (later) a conversation panel that calls the same actions as the UI.

Read before changing code: this file, `docs/spec.md` (current slice), `docs/decisions.md`.

## Principles

- **#1 DevOps first.** We plan, track and show work in DevOps; if it isn't in DevOps, it isn't planned yet. FocusTime makes the healthy path the easy path, without policing, and re-planning never feels like failure.
- **Nothing machine-specific in core modules** (`week/`, `plan/`, `actions/`, `sources/`). OS integrations (keyring, Edge/Chromium launch, notify-send, playerctl, Hyprland) stay behind thin host adapters, so a hosted version stays possible later.

## Hard rules

- All external systems are read-only, except Outlook events FocusTime created (step 12), help invites it sends to Cooptimize addresses and the time and show-as of my own events with no other attendees (step 13) and my response (accept, tentative, decline, with an optional note and proposed time) to meetings someone else invited me to (step 16), written only through the write framework (`actions/timebox-actions.ts`: preview, confirm, read back, audit log, undo; marker required on FocusTime's events, never added to mine). Meetings with other attendees are never edited: an RSVP only calls Graph's accept, tentativelyAccept or decline, never PATCH, DELETE or cancel. Azure (step 15.4): only start, deallocate and the auto-shutdown schedule's daily time and status (delay, skip, restore) of the one VM I confirmed (`actions/vm-actions.ts`, any other VM refused), with the signed-in person's own delegated access, each with preview, polling or read back and the Azure write log; no undo for power (the opposite action is offered), a changed schedule is always put back or shown on Today. DevOps (step 14): only the named writes in `actions/devops-write-actions.ts` (state, comment, create from a draft, target date on my feature or epic, and their undos), each with preview, `test /rev`, read back, audit log and undo, with my personal write PAT for that client only, never deletes. DevOps step 17 adds no new write: Save dates in Plan ahead is the same target date write with Start Date in the same patch (refused when the type has no Start Date). Teams (step 16.3): only my own preferred presence (setUserPreferredPresence Busy or DoNotDisturb, always with an expiration of the time left plus 5 minutes, and clearUserPreferredPresence), only from the focus timer (`actions/presence-actions.ts`), each logged in the Teams status log; no preview; never another person's status, never messages or posts. No writes to Dataverse, Google, other Teams data, or any other Azure resource. The plan (picks, drafts, done ticks) lives only in the local plan store.
- Teammates' free/busy (Graph getSchedule): keep only free/busy and working hours; never store, log or display subjects, locations or other details of their events. Teammates' PTO shows only as "away", never the title. Teammates' presence (step 16.3, getPresencesByUserId): only a word (Available, Busy, In a meeting, Do not disturb, Away, Be right back, Offline), read for the people on screen; never store, cache or log it, and never read or show status messages, out of office notes or work location. Profile photos (step 16.4, ProfilePhoto.Read.All): only for me and the Cooptimizers on screen, cached 7 days in `~/.cache/focustime/photos` under hashed names, cleared on sign-out, never logged or put in the plan store.
- Secrets live only in the OS keyring (service `focustime`). The one Microsoft sign-in (step 15.4) keeps its refresh token in account `outlook-refresh-token`; the ID token is read for who signed in, never stored, and only its name, address, oid and tid are kept. Access tokens in memory only. Never log, cache, export or print tokens, secrets, Authorization headers or raw HTTP bodies.
- DevOps PATs: the company read PAT is read from Dataverse only at DevOps fetch time (`devopsTargets`), and never on the write path (`{withPat:false}`). My write PATs (step 14) live only in the keyring (`devops-write-pat:<client>`), entered in Settings, checked against my DevOps identity before saving. Both are wrapped in `Pat` (prints as `[PAT]`), used only for the Authorization header to `https://dev.azure.com/<org>/`. Never logged, cached, returned to the UI, exported, or asked for in chat.
- Core views work with no AI provider. AI never executes anything; it only suggests via allowlisted actions.
- Localhost server (if any): bind 127.0.0.1, check Host and Origin, per-launch token.
- Do not touch Hyprland, Omarchy, browser profiles, Remmina or existing keyring entries.
- Client data stays scoped to its client in views and drafts.

## Working style

- Small end-to-end steps. Define behavior first; failing test where it matters (normalization, risk rules, secret handling, failure isolation, persistence); implement; refactor.
- No tests for trivial styling or that mirror implementation.
- Type-check before calling a step done. Inspect the real UI (screenshot) for UI changes.
- Verify current official docs before version-specific integration code.
- Record decisions in `docs/decisions.md` and open questions in `docs/open-questions.md` as they come up.
- Plain language in UI copy. No em dashes.
- Commit and push to `origin` (the private GitHub repo `focustime`) after each completed step.
- Never commit secrets (PATs, client secrets, tokens, Authorization headers, keyring values) or real personal or client data (real names, emails, client DevOps orgs or projects, work item titles, calendar subjects, screenshots of real data). Tests and fixtures use fakes (`@example` addresses, `contoso`/`fabrikam` orgs); screenshots in the repo come from demo mode only. Local stores, backups, footage and config stay out of git (`.gitignore`).

## Completion report per increment

Delivered behavior, changed files, verification results, checks not possible, limitations, setup and rollback steps, proposed next increment.
