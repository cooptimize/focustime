# FocusTime

FocusTime is a hosted web app for Cooptimizers: a week grid of half-day focus blocks with meetings and personal events layered on, risk flags, planning rituals, a focus timer, follow-ups, and (later) a conversation panel that calls the same actions as the UI. It is moving to Azure (docs/azure/). Developers run it locally through the developer loop (`system/README.md`).

Read before changing code: this file, `docs/spec.md` (the slices so far), `docs/decisions.md`, and for the Azure move `docs/azure/A0-plan.md`.

## Current milestone

Steps 1 to U6 and R1 are done, each authorized separately; what each delivered is in `docs/spec.md` and `docs/decisions.md`. The Azure move follows `docs/azure/A0-plan.md`: A0 (inventory and plan), A1 (the host boundary, per-user settings instead of machine defaults, per-user time zone groundwork; `docs/azure/A1-report.md`) and A2 (Entra web sign-in and sessions, user ids on every table with one filter, settings rows, per-user encrypted secrets, the scheduler; `docs/azure/A2-report.md`) A3 (the plan store on SQL Server: Azure SQL hosted, a local container here; export JSON as the migration format; the idle rule; `docs/azure/A3-report.md`) A4 (Azure infrastructure as Bicep, the image, CI and the dev deploy over OIDC, Key Vault secrets and the data key; `docs/azure/A4-report.md`, `docs/azure/runbook.md`) and A5 (prod in FocusTime with a clean database, manual deploys by SHA that promote dev's tested image, migrations only add, the local app retired, the pilot; `docs/azure/A5-report.md`) are done; A6 follows, authorized separately. Only the work in `docs/spec.md`, `docs/azure/A0-plan.md` and the authorized steps is authorized. Ask before expanding scope, adding a source, or adding a dependency not listed there.

## Principles

- **#1 DevOps first.** We plan, track and show work in DevOps; if it isn't in DevOps, it isn't planned yet. FocusTime makes the healthy path the easy path, without policing, and re-planning never feels like failure.
- **The host boundary.** Core modules (`week/`, `plan/`, `actions/`, `sources/`, `store/`, `ai/`) never touch the machine: no files, processes, sockets, keyring or desktop programs. Every such touch goes through the `Host` interface (`host/types.ts`), handed in at startup by `server/main.ts` from `FOCUSTIME_HOST=local|azure`. `host/boundary.test.ts` enforces it.
- **Per-user, not per-machine.** Working hours, standing blocks, the time zone, the VM and every other preference are the signed-in person's settings with neutral defaults, never the developer's.

## Hard rules

- All external systems are read-only, except Outlook events FocusTime created (step 12), help invites it sends to Cooptimize addresses and the time and show-as of the user's own events with no other attendees (step 13) and the user's response (accept, tentative, decline, with an optional note and proposed time) to meetings someone else invited them to (step 16), written only through the write framework (`actions/timebox-actions.ts`: preview, confirm, read back, audit log, undo; marker required on FocusTime's events, never added to the user's own). Meetings with other attendees are never edited: an RSVP only calls Graph's accept, tentativelyAccept or decline, never PATCH, DELETE or cancel. Azure (step 15.4, D475): only start the one VM the user confirmed (`actions/vm-actions.ts`, any other VM refused), with the signed-in person's own delegated access, preview, polling and the Azure write log; no undo. FocusTime never stops a VM and never writes a VM's auto-shutdown schedule (no time, status, time zone, notification or delete): the schedule is the user's own and is only read. The Azure client allows only reading the VM, its instance view, its schedule and a start's progress, the owner tag query, and start (`ALLOWED` in `sources/azure/client.ts`); anything else throws before a request is sent. DevOps (step 14): only the named writes in `actions/devops-write-actions.ts` (state, comment, create from a draft, target date on the user's feature or epic, and their undos), each with preview, `test /rev`, read back, audit log and undo, with the user's personal write PAT for that client only, never deletes. DS-1's Draft stories publishes through the same create (`proposal_create`: a story under its feature, one per kept card, after the batch preview), never an estimate. DevOps step 17 adds no new write: Save dates in Plan ahead is the same target date write with Start Date in the same patch (refused when the type has no Start Date). Teams (step 16.3): only the user's own preferred presence (setUserPreferredPresence Busy or DoNotDisturb, always with an expiration of the time left plus 5 minutes, and clearUserPreferredPresence), only from the focus timer (`actions/presence-actions.ts`), each logged in the Teams status log; no preview; never another person's status, never messages or posts. No writes to Dataverse, Google, other Teams data, or any other Azure resource. The plan (picks, drafts, done ticks) lives only in FocusTime's plan store.
- Teammates' free/busy (Graph getSchedule): keep only free/busy and working hours; never store, log or display subjects, locations or other details of their events. Teammates' PTO shows only as "away", never the title. Teammates' presence (step 16.3, getPresencesByUserId): only a word (Available, Busy, In a meeting, Do not disturb, Away, Be right back, Offline), read for the people on screen; never store, cache or log it, and never read or show status messages, out of office notes or work location. Profile photos (step 16.4, ProfilePhoto.Read.All): only for the user and the Cooptimizers on screen, cached 7 days by the host's photo cache under hashed names, cleared on sign-out, never logged or put in the plan store.
- Teams chats (T-2): read only, with delegated Chat.ReadBasic: the names, links and members (id, name, email, tenant) of the group chats registered for a client (its Delivery chats), nothing else. Never read lastMessagePreview, never post, react or mark read, never log a chat id, topic or member. Requests (AP-1, D490; shared polling, D514 to D520): a chat is registered once per client by a FocusTime admin who follows the client and is a member (one `isAdmin()` check, `actions/admin.ts`, D522; logged with who); reading is decided per chat, centrally, by an admin (`read_on`, D523; migrated chats are read only where someone had switched them on), with no per-person switch; one job reads each registered chat with a follower's own incrementally consented Chat.Read (the registrant's first, then the other followers' by name; never on the registration, never app-only, no token kept between cycles), every 5 minutes in the union of followers' working hours and never outside them (on Refresh only outside prod), only messages newer than the registration. Messages and Requests are stored once per chat in app tables (unmatched messages deleted after 14 days) and shown only to FocusTime users who are members of that chat now (its cached member list) and follow its client, enforced by the store's `viewer(userId)` (D521; following alone is never enough), never outside that client's views, never in logs, Application Insights or error messages (ids and counts only; the cycle log names only the token owner). Sent to an AI only through `ai/` (AP-2, D501): only Request candidates (under the token owner's switches and caps) and a person's own promise candidates (under theirs), one client's context at a time (5 earlier messages of that chat with authors as client, Cooptimize or me, no email addresses), only with AI for FocusTime and that client's Allow AI on; an AI draft never writes without the preview and confirm. One client's chat never shows under another.
- App secrets (the Entra, Google and Dataverse client secrets) live only in the host's secret store (`Host.secrets`: the OS keyring, service `focustime`, in the developer loop; Key Vault in the hosted app), set up outside FocusTime, never from a person's Settings. A person's secrets (their Microsoft and Google refresh tokens, their DevOps write PATs) live only sealed in `user_secrets` under the app data key from `Host.keys` (`store/user-secrets.ts`, D425), and never leave the server. The ID token is validated at sign-in and never stored; only name, UPN, email, oid and tid are kept. Access tokens in memory only, per person. Never log, cache, export or print tokens, secrets, Authorization headers or raw HTTP bodies.
- DevOps PATs: the company read PAT is read from Dataverse only at DevOps fetch time (`devopsTargets`), and never on the write path (`{withPat:false}`). Write PATs (step 14) live only in the person's sealed secrets (`devops-write-pat:<client>`, A2), entered in Settings, checked against the user's DevOps identity before saving. Both are wrapped in `Pat` (prints as `[PAT]`), used only for the Authorization header to `https://dev.azure.com/<org>/`. Never logged, cached, returned to the UI, exported, or asked for in chat.
- Core views work with no AI provider. AI never executes anything; it only suggests via allowlisted actions.
- AI (AI-0, D495 to D499): every request goes through `ai/` (`aiFor(ctx).run(task, input, schema)`), never a provider directly. Structured output only: an answer that fails its schema is a typed error, never shown and never retried. One client per request (or "none"): `ai/guard.ts` refuses another client's names, projects or item ids, secret shapes, the VM and outside email addresses before anything is sent. Runs only with AI for FocusTime on and, for a client, that client's Allow AI (both the team's, set in Admin, off by default); stops at the person's and the app's monthly caps. `store: false`. The OpenAI key is only in Key Vault (`ft-openai-key`, via `infra/scripts/openai-key.sh`) or the developer's keyring; no key means "AI isn't set up" and everything else works. The request log keeps counts, cost and outcome, never prompt or answer text.
- The server checks Host and Origin against the public URL, and every state change needs a session and its `X-CSRF` token. Sign-in is Entra OpenID Connect for the Cooptimize tenant only, or "Try the demo" (D421, D422). Every plan store statement is scoped to the session's person by `store/scope.ts`; never take a user id from the client, and never write SQL that names `user_id` (D423). A new table must be a user table with `user_id` first in its keys, or an app table, or `store/isolation.test.ts` fails.
- One source of truth per session (no-demo-leak, D442): a real session's clients come only from Dataverse and its items only from DevOps; a demo session gets only demo data, wired in one place (`server/main.ts` → `server/demo.ts` → `sources/demo/`). Nothing else that runs imports `fixtures/`, `sources/demo/`, `host/fakes.ts` or a `*fakes.ts` (`host/no-demo-leak.test.ts`). A source that fails or isn't set up says so with its fix; nothing stands in for it
- The plan store's database comes from the app config's `[database]` (or `FOCUSTIME_DB_*`), never from a person. SQL Server everywhere (Azure SQL with the app's managed identity token through `DefaultAzureCredential`; the local container with the SQL login whose password is the host secret `sql-password`); SQLite only for the demo, the fallback and the export of a local store (D428). Never put a password, token or connection string with a password in a file, an argument, a log or an error message; tokens stay in the driver's memory. Every write runs in a transaction; SQL Server changes go only through `store/sql/migrate.ts` (D429). When nobody is using FocusTime the server makes no database call but the scheduler's stored next-due check (D431).
- Migrations only add (D468): tables, columns, indexes, in a new timestamped file in `store/migrations/` (the numbered lists are frozen). A rename or a drop ships in a later release than the code that stops using it, with a `safe-drop: <reason>` comment in its file, so rolling back to the previous revision is always safe against the current database; an older build runs on a newer database. `store/migrations/additive.test.ts` fails otherwise.
- Cloud writes (A4): Azure resources change only through `infra/` (Bicep) and the deploy workflows, or the scripts in `infra/scripts/` (bootstrap, app registration, copy secrets), each idempotent; show a what-if before any create. Prod (resource group FocusTime) only through `deploy-prod.yml` with its environment approval, from A5. Never print, echo, log or pass as an argument a secret: secrets go by pipe from the keyring or `az ad app credential reset` into Key Vault. Nothing secret in the repo, the image, build args, GitHub (variables hold ids only; deploys use OIDC) or logs. Never add a SQL login or a firewall rule beyond "Azure services" (the deploy runner's own rule is removed at the end of its job); never run DDL against a hosted database except through `focustime migrate` in the workflow. Leave the "Coopilot Desktop" registration alone. From A5 on, work on a branch and open a pull request.
- Desktop-only operations (windows, programs, desktop notifications, music players, files) exist only in `host/local`; the hosted host refuses them with "not available in the hosted app". Do not touch a developer's desktop configuration, browser profiles or secret store entries other than FocusTime's own.
- Client data stays scoped to its client in views and drafts.

## Working style

- Small end-to-end steps. Define behavior first; failing test where it matters (normalization, risk rules, secret handling, failure isolation, persistence); implement; refactor.
- No tests for trivial styling or that mirror implementation.
- Type-check before calling a step done. Inspect the real UI (screenshot) for UI changes.
- Verify current official docs before version-specific integration code.
- Record decisions in `docs/decisions.md` and open questions in `docs/open-questions.md` as they come up.
- Plain language in UI copy. No em dashes.
- Commit and push to `origin` (the private GitHub repo `focustime`) after each completed step.
- Worktrees under `~/Code/focustime-wt/<branch>`; `~/Code/focustime` stays on main and runs the service. Never run builds, migrations or servers against the service's database or build folder from a worktree.
- Parallel sessions each keep to their own scope and PR.
- Inner loop: run related tests (`npx vitest related <files>` or `npx vitest --changed`) plus the typecheck. Run the full suite once before the PR; CI runs it again.
- Test data comes from the builders (`test/builders`), never hand-written fixtures. A test that starts a server takes its port through `test/ports.ts` and its own temp folder.
- One e2e per feature for the main path; edge cases are unit tests.
- Screenshots only for changed screens, at 1920 and at the largest Text size.
- New migrations get a UTC timestamp prefix (`20261103T1700_setup_state`), never the next number.
- End each report with time per phase (build, tests, e2e, screenshots, fixes).
- After a server or UI change in the developer loop: `npm run build`, `systemctl --user restart focustime`, then `focustime-open`.
- Never commit secrets (PATs, client secrets, tokens, Authorization headers, keyring values) or real personal or client data (real names, emails, client DevOps orgs or projects, work item titles, calendar subjects, screenshots of real data). Tests and fixtures use fakes (`@example` addresses, `contoso`/`fabrikam` orgs); screenshots in the repo come from demo mode only. Local stores, backups, footage and config stay out of git (`.gitignore`).

Delivered behavior, changed files, verification results, checks not possible, limitations, setup and rollback steps, proposed next increment.
