# FocusTime

FocusTime is a hosted web app for Cooptimizers: a week grid of half-day focus blocks with meetings and personal events layered on, risk flags, planning rituals, a focus timer, follow-ups, and (later) a conversation panel that calls the same actions as the UI. It is moving to Azure (docs/azure/). Developers run it locally through the developer loop (`system/README.md`).

Read before changing code: this file, `docs/technical/` (how FocusTime works: architecture, data, integrations, security, operations, development; also in the app at `#/docs`), `docs/spec.md` (the slices so far), `docs/decisions.md`, and for the Azure move `docs/azure/A0-plan.md`.

## Current milestone

FocusTime is hosted on Azure: prod in the FocusTime resource group (deployed by hand by SHA through `deploy-prod.yml`, promoting dev's tested image) and dev deployed from main; the local app is retired and developers run the developer loop. The Azure move follows `docs/azure/A0-plan.md` (A0 to A5 done, reports in `docs/azure/`; A6 follows, authorized separately).
Work goes one step per pull request: a step code (like LP-1, GD-2 or HK-7), its decisions under that code in `docs/decisions.md` (numbered at merge), its open questions in `docs/open-questions.md`, each step authorized separately. What each delivered is in `docs/spec.md` and `docs/decisions.md`; `docs/technical/` is the reference for how FocusTime works now.
Only the work in `docs/spec.md`, `docs/azure/A0-plan.md` and the authorized steps is authorized. Ask before expanding scope, adding a source, or adding a dependency not listed there.

## Principles

- **#1 DevOps first.** We plan, track and show work in DevOps; if it isn't in DevOps, it isn't planned yet. FocusTime makes the healthy path the easy path, without policing, and re-planning never feels like failure.
- **The host boundary.** Core modules (`week/`, `plan/`, `actions/`, `sources/`, `store/`, `ai/`) never touch the machine: no files, processes, sockets, keyring or desktop programs. Every such touch goes through the `Host` interface (`host/types.ts`), handed in at startup by `server/main.ts` from `FOCUSTIME_HOST=local|azure`. `host/boundary.test.ts` enforces it.
- **Per-user, not per-machine.** Working hours, standing blocks, the time zone, the VM and every other preference are the signed-in person's settings with neutral defaults, never the developer's.

- The server checks Host and Origin against the public URL, and every state change needs a session and its `X-CSRF` token. Sign-in is Entra OpenID Connect for the Cooptimize tenant only, or "Try the demo" (D421, D422). Every plan store statement is scoped to the session's person by `store/scope.ts`; never take a user id from the client, and never write SQL that names `user_id` (D423). A new table must be a user table with `user_id` first in its keys, or an app table, or `store/isolation.test.ts` fails.
- One source of truth per session (no-demo-leak, D442): a real session's clients come only from Dataverse and its items only from DevOps; a demo session gets only demo data, wired in one place (`server/main.ts` → `server/demo.ts` → `sources/demo/`). Nothing else that runs imports `fixtures/`, `sources/demo/`, `host/fakes.ts` or a `*fakes.ts` (`host/no-demo-leak.test.ts`). A source that fails or isn't set up says so with its fix; nothing stands in for it
- The plan store's database comes from the app config's `[database]` (or `FOCUSTIME_DB_*`), never from a person. SQL Server everywhere (Azure SQL with the app's managed identity token through `DefaultAzureCredential`; the local container with the SQL login whose password is the host secret `sql-password`); SQLite only for the demo, the fallback and the export of a local store (D428). Never put a password, token or connection string with a password in a file, an argument, a log or an error message; tokens stay in the driver's memory. Every write runs in a transaction; SQL Server changes go only through `store/sql/migrate.ts` (D429). When nobody is using FocusTime the server makes no database call but the scheduler's stored next-due check (D431).
- Migrations only add (D468): tables, columns, indexes, in a new timestamped file in `store/migrations/` (the numbered lists are frozen). A rename or a drop ships in a later release than the code that stops using it, with a `safe-drop: <reason>` comment in its file, so rolling back to the previous revision is always safe against the current database; an older build runs on a newer database. `store/migrations/additive.test.ts` fails otherwise.
- Cloud writes (A4): Azure resources change only through `infra/` (Bicep) and the deploy workflows, or the scripts in `infra/scripts/` (bootstrap, app registration, copy secrets), each idempotent; show a what-if before any create. Prod (resource group FocusTime) only through `deploy-prod.yml` with its environment approval, from A5. Never print, echo, log or pass as an argument a secret: secrets go by pipe from the keyring or `az ad app credential reset` into Key Vault. Nothing secret in the repo, the image, build args, GitHub (variables hold ids only; deploys use OIDC) or logs. Never add a SQL login or a firewall rule beyond "Azure services" (the deploy runner's own rule is removed at the end of its job); never run DDL against a hosted database except through `focustime migrate` in the workflow. Leave the "Coopilot Desktop" registration alone. From A5 on, work on a branch and open a pull request.
- Outside production, nothing happens on its own (ENV-1). Production is `FOCUSTIME_ENV` exactly `prod`; anything else, empty or missing is a test site. On a test site FocusTime does nothing unprompted that reaches a person (a Teams message, Web Push, a reminder or notice), spends AI, writes to an outside system (Teams status included) or reads a person's delegated data on a schedule (chats, calendars for capture, transcripts); a person pressing a button still works and acts only for that person. Reminders, Web Push and Teams bot messages go only to a person who switched on "Send me reminders and Teams messages from this test site"; the DevOps store polls only while someone uses that deployment; `FOCUSTIME_REQUESTS_POLL=on` declares a chat watch period and nothing else. The decision lives only in `config/background-policy.ts`, handed out by `server/main.ts`. Any new background work (a scheduler job, a tick part, work at start) gets a named entry in `BACKGROUND` first, or it doesn't run outside production and `config/background-policy.test.ts` fails.
- Desktop-only operations (windows, programs, desktop notifications, music players, files) exist only in `host/local`; the hosted host refuses them with "not available in the hosted app". Do not touch a developer's desktop configuration, browser profiles or secret store entries other than FocusTime's own.
- The client boundary (GD-2, replacing GD-1's one-line rule for sorting and AI drafting):
  1. The audience decides, from real membership. A chat whose members are all Cooptimizers is internal. Any guest or outside member makes it client-facing. Use the existing Cooptimizer rules (guests and automation accounts aren't Cooptimizers). Re-check membership when it changes.
  2. Internal chats: sort messages normally, keeping cross-client mentions.
  3. Client-facing chats: a message that names another client is held back, as today, but visible (Part 2) and sortable by hand.
  4. Only words travel. When sorting or drafting for one client, never pull another client's records (items, conversations, promises, transcripts) into the prompt. A mention in a message's own text is allowed for internal chats.
  5. AI-written DevOps text for a client never names another client:
     - the generation prompt says so
     - a check after generation replaces any other client's name or alias with "another client" and marks the draft ("Another client's name was removed") so the person sees it
     - Internal (Cooptimize) work is the exception and may name clients
  6. Every exit to client eyes is checked: Close the loop posts and emails, DevOps writes into a client's org, and text that feeds the client status report.
     - If another client's name appears, the preview flags it with one click to replace it with "another client".
     - Text the person typed can still be sent after they've seen the flag; AI-generated text follows point 5 (AI-written DevOps text).
  7. A conversation that mentions another client shows a small "mentions <client>" tag to whoever can already see that conversation.

  Unchanged: admins never see others' content, client views only show that client's records, no automatic posting to client chats.

## Working style

- Never run anything in ~/Code/focustime except git fetch, and never rebuild or restart the local service, unless the product owner asks.
- Small end-to-end steps. Define behavior first; failing test where it matters (normalization, risk rules, secret handling, failure isolation, persistence); implement; refactor.
- No tests for trivial styling or that mirror implementation.
- Type-check before calling a step done. Inspect the real UI (screenshot) for UI changes.
- UI steps that touch Day, Week or the block panel follow `docs/design/style-guide.md` section 10 (Day and Week: rules for people, PS-1): one time and date format, one name per thing, one main button, minimum targets.
- Verify current official docs before version-specific integration code.
- Record decisions in `docs/decisions.md` and open questions in `docs/open-questions.md` as they come up.
- Plain language in UI copy. No em dashes.
- Commit and push to `origin` (the private GitHub repo `focustime`) after each completed step.
- Worktrees under `~/Code/focustime-wt/<branch>`; `~/Code/focustime` stays on main and runs the service. Never run builds, migrations or servers against the service's database or build folder from a worktree.
- Parallel sessions each keep to their own scope and PR.
- Inner loop: run related tests (`npx vitest related <files>` or `npx vitest --changed`) plus the typecheck. Run the full suite once before the PR; CI runs it again.
- Test data comes from the builders (`test/builders`), never hand-written fixtures. A test that starts a server takes its port through `test/ports.ts` and its own temp folder.
- One e2e per feature for the main path; edge cases are unit tests.
- Screenshots only for changed screens, at 1920 and at the largest Text size.
- New migrations get a UTC timestamp prefix (`20261103T1700_setup_state`), never the next number.
- End each report with time per phase (build, tests, e2e, screenshots, fixes).
- After a server or UI change in the developer loop: `npm run build`, `systemctl --user restart focustime`, then `focustime-open`.
- Never commit secrets (PATs, client secrets, tokens, Authorization headers, keyring values) or real personal or client data (real names, emails, client DevOps orgs or projects, work item titles, calendar subjects, screenshots of real data). Tests and fixtures use fakes (`@example` addresses, `contoso`/`fabrikam` orgs); screenshots in the repo come from demo mode only. Local stores, backups, footage and config stay out of git (`.gitignore`).
