## CI-2: Browser jobs survive a package server outage (Nov 11)

Unnumbered until merge.

| # | Status | Decision |
|---|---|---|
| - | Done | CI-2: why. On Nov 11 all six browser shards of PR #128's run failed at "Install WebKit's system packages": `Temporary failure resolving 'archive.ubuntu.com'` (and `azure.archive`, `security`). The cache was an exact hit (185 packages, 139 MB), but `install-deps` runs `apt-get update` and then installs what apt's lists call newest. The lists named a libsoup security update (`3.6.6-1ubuntu0.1`, 303 kB) newer than the cached one, so apt went to a mirror it couldn't reach. A cache keyed on the runner image can't fix that on its own: the archive moves between image releases. |
| - | Done | CI-2: the step is `scripts/ci-webkit-deps.sh`. Offline first: when the cache's stamp names this runner image and Playwright version and every file matches its sha256 manifest (and nothing extra is there), it installs exactly the cached files with `dpkg -i` (the newest file per package, skipping any already installed at that version or newer) and checks the result (below). If it's complete, the step is done with no network. |
| - | Done | CI-2: otherwise the usual way: `npx playwright-core install-deps webkit`, seeded with the cached files, at most 3 attempts of 3 minutes each (a slow mirror that never fails is cut off), 20 and 40 s apart, with `dpkg --configure -a` and `apt-get -f install --no-download` between them. A damaged cache, one from another image or Playwright version, or an offline install that isn't complete (a stale cache) all fall through to this path. If all three attempts fail too (an outage on a new image or Playwright version), the last resort is whatever cache was restored, from any image, with no network, accepted only when the check passes (`took the fallback path`). |
| - | Done | CI-2: done means complete, not only a launch: every package Playwright's own `install-deps --dry-run webkit` names is installed (one it names only because apt's lists know a newer version counts as installed), and WebKit launches headless and renders a page (one retry for a slow first start). A partial install can start WebKit and still miss fonts or media libraries. |
| - | Done | CI-2: the cache is rewritten only after the usual way: exactly the installed version of each file apt holds, its manifest, then the stamp, built beside the old one and swapped in. Its key ends in a hash of stamp and manifest (`apt-webkit2-<image>-<playwright>-<hash>`), restored by prefix, so a rewritten cache is a new entry and the newest wins (the old `apt-webkit-` key was immutable, so a stale cache could never be replaced). Shards that rewrite the same packages share a key; the save that loses the race only warns (`continue-on-error`). ci.yml saves only from main (a push, or deploy-dev calling it): a pull request's cache would be scoped to its own ref, used by nobody else, and evict the npm and browser caches. The packages are then pinned to what the first run on a runner image installed, so a security update arrives with the next image (about weekly). Local .deb files skip apt's signature check; that is safe because only main writes main's caches. |
| - | Done | CI-2: the step says in its last line which path it took (`webkit-deps: took the offline path: …` or `took the online path: …`). The browser is installed before the packages step now, since that step launches it. |
| - | Done | CI-2: the proof is its own workflow, `ci-webkit-deps.yml`, on pull requests that change the script or the CI workflows and on manual dispatch. One leg starts with an empty cache and the network open, requires the usual way, and saves the cache. The next leg checks it runs on the same runner image (GitHub rolls images out over days; a mismatch fails and asks for a re-run), restores exactly that cache, points every host in apt's mirror list and sources (plus Ubuntu's own names) at 127.0.0.1 and ::1, checks none answers and apt can't download, and requires the offline path and a complete install. It also runs when `package.json` or `package-lock.json` changes (a new Playwright version). It isn't part of ci's gate or deploy-dev. |
| - | Done | CI-2: unchanged: what CI tests, the six shards, the tree check (D456), deploy-dev's and deploy-prod's steps, Azure and secrets. |
| - | Done | CI-2: Playwright's docs (playwright.dev/docs/test-cli, /docs/ci, /docs/docker, read Nov 11) document only `--dry-run` for `install-deps`, and no way to list or pin a browser's packages. `--dry-run` simulates with `apt-get install -s` against apt's lists, so it also names a package that is installed but has a newer version in the lists; the script counts those as installed (dpkg says so) and treats only the rest as missing. The docs also say OS packages "are not cacheable" and don't recommend caching browsers; FocusTime caches the .deb files anyway (AP-2), which is what makes the offline path possible. |
| - | Open | CI-2: Playwright's image (`mcr.microsoft.com/playwright:v1.64.1-resolute`, Ubuntu 26.04) would carry the packages and the browsers and is what the docs recommend for containers. The docs don't say which Node it carries, and these jobs need Node 26 (`actions/setup-node` inside it would download Node each run); pulling about 2 GB per shard may also cost more than the 25 s the step takes today. Not switched in this step. |
| - | Done | CI-2: `dpkg -i`, not `apt-get install --no-download ./x.deb`: the first proof run showed apt preferring the runner's lists' amd64v3 builds of the same versions over the local files and trying to fetch them with downloads off ("Unable to fetch some archives"). dpkg reads only the files and what is installed. |
| - | Done | CI-2: measured on PR #129. Before (30 shard runs on Nov 11): the cache restore and install step together took 27 s on average, 71 s at most. After, offline (all six shards): 25 s on average, 33 s at most. After, online (the first run on a runner image or Playwright version, about weekly): 45 s on average (the completeness check and the cache rewrite add about 20 s). Until main saves a cache for a new image, pull requests take the online path, since they don't save. |
| - | Done | CI-2: `e2e/wd2.test.ts`'s `week()` and `day()` set the address once after a reload and waited 30 s. Set between the app's first render and its effects (the hashchange listener is a passive effect), the app pushed its own address over it, so the page never came. Under a loaded runner that failed shard 2 four times in five on this PR, a different test each time (and once on main, Nov 11 17:56). They now set it again, every 250 ms while the page hasn't shown, whenever the address isn't the one asked for. Outside this step's first scope (`.github/`, `scripts/`, docs), taken once QT-1 had merged, because the PR's checks couldn't pass without it. Other browser tests that set the address after a reload may have the same gap. |
| - | Done | CI-2 review (a fresh subagent with only the diff): fixed a launch-only check that let a partial install pass, the proof failing when its legs land on different runner images, the proof not running on a Playwright bump, no last resort during an outage on a new image, a broken install not repaired with the network before a retry, one slow first launch sending a good offline install online, PR caches filling the cache space, and smaller things (`DEBIAN_FRONTEND`, `dpkg-deb -W`, a relative cache path, an unknown image matching across images). |
