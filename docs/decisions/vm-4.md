## VM-4: Why the VM chip says Unknown, and a bare bad request (Nov 17)

Unnumbered until merge.

| # | Status | Decision |
|---|---|---|
| - | Done | The cause, "bad request": Close out's check-in answer wrote `stamp()`, a zoned time like `2026-11-02T08:01:00-05:00[America/New_York]` (43 characters), into `timeboxes.settled_at`, `nvarchar(40)` on SQL Server; SQL Server refused it and the action route turned every thrown error into 400 "bad request". SQLite doesn't check lengths, so the tests missed it. Fixed: `settled_at` is written as an instant to the second (`settledAt()` in `store/plan-store.ts`), which every reader already parses; a SQL Server test answers a check-in in New York's zone. No migration, nothing dropped. |
| - | Done | The cause, Unknown: from 21:11 UTC Azure answered 403 to about one read in four of the VM's state (the same token answering 200 a minute either side, `docs/ux/vm4/what-happened.md`), and FocusTime showed any failed read as Unknown at once and kept it for a minute; after a failed request the page never asked again until the tab was hidden and shown. Why Azure refused isn't in the logs (open question); its error code is now logged as `kind` on failed Azure calls (`azureCodeWord`: one plain word, else `other`, or `none`). |
| - | Done | A failed read keeps the last state read (the server's memo, and the page's own when the server has none or doesn't answer), with a hollow mark and "Read <how long> ago", and asks again in 10 s (`CHECK_AGAIN_MS`). After 2 minutes (`PROBLEM_AFTER_MS`) the chip's face says the reason and asks every 30 s (`CHECK_LATER_MS`): Can't reach Azure (network, a time-out, the stored sign-in unreadable), Azure is busy (429 or 5xx), Sign in to Azure again (no sign-in, consent, expired), Azure refused (anything else); the page adds Can't reach FocusTime when its own request fails. A consent problem shows Allow Azure access at once, as before. "Unknown" only when Azure answers with no state. One list, `READ_PROBLEM` in `plan/vm.ts`. |
| - | Done | Start and Stop are offered from the last good reading while checking, and each reads Azure afresh: the preview reads the state and offers only what that state allows, and the confirm reads it again and refuses when it changed (both as before VM-4; tests in `actions/vm4-chip.test.ts`). Nothing is started or stopped on an old reading. |
| - | Done | "Read 1 minute ago" and the 2 minutes are on the page's clock: the server sends when it answered (`answeredAt`) and the page moves the read's time by the difference (`onPageClock`, `ui/vm-status.ts`), so a server and a browser whose clocks disagree still say the right age. Found in the pictures (the demo's own clock said "369 hours ago"). |
| - | Done | After a restart the first answer is "Checking…" with no state (never Unknown), then the state. The step 15.4 consent test now expects that instead of `chip: "unknown"`. |
| - | Done | The automatic start reads the state before it claims the day. A read that fails at the planned time isn't the day's try: logged once as `state_unreadable`, shown in Settings ("Today's start is waiting…") and read again on later passes; still unreadable at the late limit, `state_unreadable_late`, told once ("Left off today: FocusTime couldn't read your VM's state"). Which reads retry: any failure but a sign-in one (no sign-in, consent, expired, not connected) and a 404, so a 403, a 429, a 5xx, a time-out, a network failure and an unreadable stored sign-in all wait for a later pass; before, they ended the day as `refused`. The state read before the claim stands in for the start's own read only within 5 seconds (`BEFORE_FRESH_MS`): a claim that waited on the database means the start reads Azure again (found by the first review). A start sent to Azure is the day's try, as before. A sign-in that can't be used is still VM-2's `sign_in` (the day used, the person told); a VM Azure says isn't there (404) is still `no_vm`. Nothing else changes: production only, opt-in, only when stopped, never a stop, never the auto-shutdown, the person's own sign-in, every start in the write log. VM-3's guarantees are kept: the start's turn first, a stuck part can't hold a pass, each reason logged once a day. |
| - | Done | No bare "bad request". An action that throws answers 500 with "That didn't work: FocusTime ran into a problem it didn't expect. The exception item carries `ref` too. Any other `/api/` request that throws answers the same JSON. A request body that isn't JSON keeps a 400 of its own ("FocusTime couldn't read that request. Reload the page and try again."), and an action's own refusals are unchanged. Words in `server/unexpected.ts`. |
