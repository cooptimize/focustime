## VM-3: Why the VM didn't start: found, fixed and said (Nov 17)

Unnumbered until merge.

| # | Status | Decision |
|---|---|---|
| - | Done | Why: production's first automatic start (Nov 17, 8:55 AM Eastern) didn't run and said nothing. Production's logs were read only (counts, kinds and times; `docs/ux/vm3/what-happened.md`): the scheduler woke at 8:55 and both passes finished in about 3 seconds, with no `vm_autostart` line and no single-day holidays read |
| - | Done | The cause: the background start read PTO with the person's raw settings. A hosted person's Dataverse user is kept with their sign-in, and only requests added it (`withSignedIn`, `actions/dispatch.ts`), so PTO came back unknown and the start left the VM off as "not due", which was never logged. Fixed: the tick reads its settings through the same `withSignedIn` as a request (`server/ticks.ts`). `server/ticks-vm3.test.ts` lead 1 failed on main and passes |
| - | Done | The start goes first: it is the first slow part (`vm_autostart` in `SLOW_PARTS`), and the scheduler runs everyone's start (`early`) before the app jobs and before people's other parts in every slow pass |
| - | Done | Every part runs on its own (`runPart`, `server/ticks.ts`): a part that throws is logged `tick_part <name>_failed` and the parts after it run; a part over its limit is logged `tick_part <name>_over_limit`, left behind and not started again until it ends. Limits per part (`PART_LIMIT_MS`): the VM start 2 minutes, reminders 3, the Teams rhythm, the chat cleanup and meetings 2, the rest 60 seconds; the fast parts 30 seconds. Picked from production's job durations (the chats job takes about 50 seconds) |
| - | Done | The scheduler (`server/scheduler.ts`): limits for a fast pass (2 minutes), a slow pass (10), a job (5), the starts (3), a wake (30 seconds) and maintenance (5). A pass still running after its limit no longer stops the next one: it is logged `<pass>_over_limit` once and the next pass starts; when it ends late, `<pass>_finished_late`; one that took over half its limit, `<pass>_slow`. A job, a person's start and a person's other parts each run at most once at a time (busy keys), so a stuck one is skipped, never run twice; one person's stuck work never stops another's |
| - | Done | The reasons are one closed list (`OUTCOMES`, `plan/vm-autostart.ts`): started, started late, already on, not a day you chose, skipped, paused, PTO, holiday, PTO unreadable, sign-in, no VM, Azure refused, FocusTime wasn't running. Each has its log word, whether the person is told, whether the day counts as tried, and its words |
| - | Done | From the planned time on, each outcome is logged once a day per reason (`azure vm_autostart <word>`, plus `holidays_unchecked` and `pto_earlier` when they apply), never every 30 seconds, never with a name or an id. Before the planned time nothing is decided or logged |
| - | Done | Today's outcome is kept in the auto-start's own stored state (`vm_autostart`: `outcome`, `logged`, `ptoRead`; no migration) and is today's only: the next day it is ignored and replaced |
| - | Done | The person is told why when the planned time passed and FocusTime didn't start the VM, unless it was already on or it was their own choice (off, a day not chosen, skipped, paused). Told: PTO, holiday, PTO unreadable, sign-in, no VM, refused, not running. Where: the chip's "!" and title until its menu is opened, a menu line with the reason (Why shows what to do), one notice when notices are allowed (held until they are, that day only; "Your VM was left off", or VM-2's "Auto-start couldn't sign in to Azure" and "Auto-start couldn't start your VM", whose words are kept), and Settings' line where "Next:" is |
| - | Done | "Next:" never shows a passed time as still to come. Once today's planned time is behind it says what happened ("Started today at 8:55 AM.", "Left off today: it is PTO.", "Today's start (8:55 AM) hasn't run yet.") and then the next day's time. It says when PTO ("so a day off may still show a time") or holidays couldn't be read |

The status keeps a fresh read at most every 30 minutes, in production only |
