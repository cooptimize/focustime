## PK-4: Your Pocket recordings, found by themselves and counted as yours (Nov 18)

Unnumbered until merge.

| # | Status | Decision |
|---|---|---|
| - | Done | What went wrong on Nov 18. The product owner connected their Pocket, pressed Get my Pocket recordings and was told none were theirs: "18 recordings by other people were left out." The rule that chose whose recordings to list (MC-2b's `whoseKept`) was a guess made without a real answer from Pocket: it kept a recording only when its recorder was an address FocusTime knows the person by, or when every listed item named the same recorder. One item with no recorder, or a personal Pocket address FocusTime doesn't know, made it keep nothing. It failed closed in the most common case. |
| - | Done | What Pocket's docs say (read Nov 18, 2026). [List recordings](https://docs.heypocketai.com/docs/api/recordings/list-recordings): `recorded_by` holds `display_name`, `email` and `user_id`; whether it can be null isn't stated; no other field on a record says whose it is (`created_at`, `duration`, `folder_id`, `id`, `language`, `recorded_by`, `recording_at`, `speakers`, `state`, `summarizations`, `tags`, `title`, `transcript`, `translation` and their errors); `state` is a string with no values listed; summaries and uploads aren't separate items; the list takes `start_date`, `end_date`, `tag_ids`, `page` and `limit` (at most 100), with no filter by person. [Get recording details](https://docs.heypocketai.com/docs/api/recordings/get-recording-details): the same record, with `include_transcript` and `include_summarizations`. [List organization users](https://docs.heypocketai.com/docs/api/users/list-organization-users) needs an organization key with `users:read` and says "User API keys are rejected", the first place the docs name user keys. [Organization API keys](https://docs.heypocketai.com/docs/api/organization/api-keys) lists an organization's keys; nothing says what a personal key lists. The [webhooks page](https://docs.heypocketai.com/docs/api/webhooks) gives a recording's owner as a top-level `user`, which the list doesn't carry. |
| - | Done | An item is a recording only with a length above 0 and a time it was recorded. One that isn't is never a row and never counts as someone else's; it is counted apart. `state` isn't read: the docs give it no values, so nothing could be decided from it. |
| - | Done | Whose recordings are kept (`whoseKept` in `plan/pocket-recordings.ts`). Mine: the recorder is an address FocusTime knows me by (my sign-in's email and UPN) or one I set as my Pocket address. When no recording is mine by address and every recording that names a recorder names the same one, they are all kept (MC-2b's reading for a key someone made for themselves), unless that one is an address another FocusTime person is known by. A record with no recorder doesn't decide anything: it is kept when everything else under the key is kept, and left out otherwise. Otherwise nothing more is kept. |
| - | Done | What is read of an item. Its recorder's address first. Whether it is a recording (its length and time) is asked only where the addresses don't settle whose it is. Once mine are found by address, nothing of an item under another address is read but that address; it counts as "under another address" even when it isn't a recording. Of a kept recording, its id, time, length and title, as before. |
| - | Done | The line at the list's head says what was found in counts, never names: "18 listed. 16 are under an address FocusTime doesn't know you by. 2 have no recorder." (and "1 isn't a recording"), with Set my Pocket address while anything is under an unknown address and there is room for another. |
| - | Done | Set my Pocket address (`meeting.pocket_address_add`). I type it. It is accepted only when its hash is among the recorders of the list just read for me (the hold keeps the recorders as SHA-256 hashes, 5 minutes, never the addresses) and it isn't an address another FocusTime person is known by. Anything else is refused in the same words, so a refusal never says whose an address is. Five refusals a list, then "Check Pocket again in a few minutes". Up to 3 addresses. Kept sealed as `pocket-addresses` in `user_secrets`, beside the key, mine alone; never shown to an admin; removed with Disconnect and with Delete my data; never in Export (secrets aren't). Settings › Connections › Pocket recorder lists them, each with Remove (`meeting.pocket_address_remove`). Pocket isn't asked by either. |
| - | Done | Looking by itself. With Pocket connected, Calls asks for my list as it opens and on Refresh; the button is Check Pocket again and the line says when Pocket was checked. The server answers from the list it holds for me if it is under 5 minutes old and was sorted with the same Pocket addresses, so at most one list in 5 minutes, plus one after an address changes. Never on a schedule, in a job, from the assistant or the Teams bot, or for someone without Pocket connected; no entry in `config/background-policy.ts`. One recording is still read only on Continue. A failed list is one quiet line at the list's head with Check Pocket again; the list and Teams' check go on without it. |
| - | Done | A recording and its call go together when they overlap for at least half the call (as MC-2b), or when at least half the recording's own length, and at least 5 minutes of it, falls inside the call (`goesWith` in `plan/pocket-match.ts`). The server checks again on Continue with the same rule. |
