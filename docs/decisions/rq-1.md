## RQ-1: Needed fields asked before DevOps refuses, and Break down from a call (Nov 17)

Unnumbered until merge.

| # | Status | Decision |
|---|---|---|
| - | Done | Why: a client's process can require a field through a rule (for example Target Date on every new Feature and User Story) that the type's field list doesn't mark always required. The New form said "Optional" and DevOps refused the create at Confirm with its own text. |
| - | Done | STEP 0.3, what the docs say. The Work Items Create and Update pages (https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/create?view=azure-devops-rest-7.1, https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/update?view=azure-devops-rest-7.1) list `validateOnly` as a query parameter: "Indicate if you only want to validate the changes without saving the work item"; the scope is `vso.work_write`, which the write PAT already has. The rules page (https://learn.microsoft.com/en-us/azure/devops/organizations/settings/work/rule-reference) says "Constraints are evaluated on the server on work item save, and if any constraint is violated the save operation is rejected" and that rules apply through the API as on the form. The field guide (https://learn.microsoft.com/en-us/azure/devops/boards/work-items/guidance/work-item-field) has no rule errors. Not documented: the error's status and body, whether it names every field or only the first, and validateOnly's own answer. FocusTime reads all three shapes seen in DevOps answers (`customProperties.RuleValidationErrors[{fieldReferenceName, errorMessage}]`, `customProperties.FieldReferenceName`, and "TF401320: Rule Error for field <name>.") and asks again when only the first is named. A real org's answer is an open question. |
| - | Done | The check is one function: `checkCreatePath` and `writer.checkCreate` in `sources/devops/write.ts` build the create's URL with `validateOnly=true` and can't build it without; nothing else calls the create path for a check. It is not a write: nothing goes in the write log, there is no Undo, and the log line is `{source:"devops", op:"check", kind:"create", status, durationMs}` only, never the fields, the patch or the token. |
| - | Done | One place on the server: `devops.preview` runs the check for every change whose preview is a create (`new_item`, a draft's `create`, Break down's `proposal_create`, `request_create`, `meeting_create`, `conversation_create`), after the client boundary and before the preview is held; Send feedback's preview does the same. A unit test fails if a third `hold()` appears or one stops following `requireNeeded`. A create that still needs fields is refused with code `required_field` and the fields (`needed`), so screens mark them. |
| - | Done | The early check: `devops.needed` makes the same check when a form or row opens, with only a title ("FocusTime check" while the title is empty), kept about 10 minutes per person, organization, project, type and patch (only checked answers, in memory, per writer). It answers `{checked:false}` with nothing when it can't be made (no write PAT, DevOps not answering), and the form works as before and says nothing. The check at preview decides; its answer replaces the early one for the same item. |
| - | Done | A screen asks again as fields are filled (debounced, at most 6 times while it is open), so a DevOps that names only the first failing field is followed one field at a time. Free text goes to the early check only as filled or not. |
| - | Done | The type's always-required list stays as a first hint (shown before DevOps answers, and used when it can't); where DevOps answers, DevOps wins. When DevOps names only one field, the hint's other fields are kept so a person goes round once. |
| - | Done | Words: "Needed" beside the label, "Required by this client's process" under it, kept once filled; other fields still say "Optional". A field FocusTime has no control for is said in words with a way out (create it in DevOps, or save a draft). The words are in `plan/needed.ts`, a call's buttons in `plan/call-words.ts`, listed in `docs/design/wording.md`. No client, type, state or field name is written into the code: fields come from DevOps by reference name, matched to FocusTime's controls through the type's own fields (`detectTargetField`, `detectTypeSizeField`). |
| - | Done | The New form shows Start date only when the check says it's needed (a draft's own start date is kept). The draft editor marks what it has (a feature's dates, the description, a story's third question); for a field only the New form has, Create in DevOps opens the New form for that draft. A call's row marks Needed on its own fields; the start date, which a row can't fill, is said in words. |
| - | Done | A refusal at Confirm: the field in plain words ("DevOps says Target Date is needed on a new Feature. Fill it in and try again."), never DevOps's text; the result carries the field (`DevOpsResult.needed`) and the preview offers Try again instead of Retry, which closes it and returns to the form or row with what was typed and the field marked. Stored older failures read in plain words in Settings › Activity (`devops.log`). |
| - | Done | Break down: Review asks once for a story under the feature, shows each needed value field (target date, start date, size) on every card and once above them with Use for all, and starts the cards from the feature's own date where it has one. Preview waits until every kept story has its values. `stories.save` takes each card's `values` (checked: dates, start not after target, size 0 to 10000); `proposal_create` writes them through the type's own fields and refuses plainly when the type lacks one. The AI's input is unchanged. Story drafts keep their cards as JSON, so no migration. |
| - | Done | The three questions show at story level only (the client's requirement level, by `isStoryLevel` on the process levels, tested with a client whose levels are named differently): the New form, the draft editor and a call's rows. Above it `new_item` neither shows nor writes them; answers stored on features are kept and not shown. On a call's row they take the row's full width, label beside box. |
| - | Done | Create and break down, on a call's row at the feature tier (the lowest portfolio level, `isFeatureTier`): the feature goes through the one preview; once it is confirmed and written, Break down opens on it with Run started. Not now, a refusal or a failure opens nothing. A feature already created from the call keeps a Break down button on its row. The stories go in Break down's own preview, as before. |
| - | Done | The first download grew to 337.4 kB gzipped (the New form's and a call row's needed fields load with the first screen), 0.4 kB over the 337.0 kB limit; the limit was recorded again with `node scripts/first-download.ts --write` (now 348.0 kB script, 88.0 kB styles). |
| - | Done | Updates of existing items are not checked (the brief's reading that changes less); see open questions. No new dependency and no migration. Demo: `FOCUSTIME_DEMO_DEVOPS_RULES=target` gives Northwind's features and stories a Target Date rule for tests and pictures; the demo DevOps answers validateOnly as DevOps does, saving nothing. |
