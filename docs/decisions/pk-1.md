| # | Status | Decision |
|---|---|---|
| - | Done | Why: some client calls are organized by someone else, so Teams gives FocusTime no transcript. The product owner records those on the Pocket recorder ("it comes in a zip and it is a pdf. can you allow intake of this"), and a teammate uses it too. Anyone at Cooptimize who is a call's reviewer can upload one; who sees it and for how long is as for every transcript. |
| - | Done | What comes in: Pocket's export as downloaded (a .zip holding one PDF) and that PDF alone, beside .vtt and .docx, in the same upload (`POST /api/meetings/upload`), by the same people (a call's reviewers), for the same calls (registered ones). The upload's 5 MB limit is unchanged. |
| - | Done | The kind of a file comes from its first bytes (`kindOf`), never its name; the page no longer sends a name. A .vtt or .docx with the wrong extension still reads; a file named .pdf that isn't one is refused. |
| - | Done | A zip that isn't a .docx: at most 20 entries, 20 MB unpacked in all (counted as each entry inflates, whatever its header says), no archive inside (a zip that isn't a .docx, gzip, 7z, rar, bzip2, xz, zstd, tar), exactly one file FocusTime reads (a PDF, a .vtt or a .docx); folders and other files are allowed and ignored. Encrypted and Zip64 entries are refused. Read with today's node:zlib reader, extended (STEP 0.3), so no zip dependency. An entry's name is only compared, never a path; nothing is written to disk. |
| - | Done | STEP 0.3: before PK-1 the .docx reader (`zipEntry`) found one entry by name in the central directory and inflated it with `maxOutputLength` 20 MB. Safe for that one entry (a bomb stops at 20 MB, names never used as paths, nothing on disk), but it had no entry count limit, no total across entries, no check for an archive inside and no encrypted-entry check, and it trusted the header's size for a stored entry. PK-1 adds a directory walk with those limits (`zipDirectory`, `entryBytes`) and keeps the .docx path on it (its own walk bounded at 5000 entries; only word/document.xml is inflated). |
| - | Done | The PDF reader is `pdfjs-dist` 6.5.438 (Mozilla's pdf.js, Apache-2.0, released Nov 1, 2026): maintained, pure JavaScript with no build step, no network of its own when given the bytes, and it reads text in embedded Type0 fonts with an Identity-H encoding through their ToUnicode maps (tested with such a font made in the test). Not chosen: `pdf-parse` (wraps an older pdf.js and requires `@napi-rs/canvas`, a native package), `unpdf` (its pdf.js comes bundled but it lists `pdfjs-dist` as a peer, so it would add both), `pdf2json` (a fork of an old pdf.js). Its size: 37.6 MB unpacked (builds for several targets, maps and types); its optional `@napi-rs/canvas` (a prebuilt binary for drawing, no build step) installs with it and is never loaded. The only new dependency. |
| - | Done | The PDF is read in a worker thread started for that one file (`server/pdf-text.ts`, handed to the meeting actions as `readPdf`, so the core modules start no thread: the host boundary), with its own memory limit, ended after 10 seconds or its answer. Only `getTextContent` per page; at most 500 pages (counted before any page is read); no WebAssembly decoders, no fonts loaded, no XFA; pdf.js 6 has no eval path. Scripts, links, forms, launch actions and attachments are never asked for. `fetch` and the http and https modules throw in the thread before pdf.js loads, and are counted (a test checks a PDF full of links and actions reaches a local server zero times). pdf.js's own output is discarded: it can quote a file. |
| - | Done | Reading Pocket's text (`plan/pocket.ts`): the page's text items are put into lines by their position. Turns become lines by `linesOf` (merging, splitting at 1200 characters, numbering, the 4000 line limit). |
