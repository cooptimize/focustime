## TP-1: Work templates, the four lines at create (Nov 12)

Unnumbered until merge.

| # | Status | Decision |
|---|---|---|
| - | Done | TP-1: why. Tanner (Nov 12) asked for editable templates, examples and tooltips, and drop-downs instead of free text in the New form. Two studies of 1,441 work items found acceptance criteria on 5% of them: most items are a title, and the builder has to come back and ask. Four short lines are the smallest thing a builder can use: What and where, What changes, How we'll check, How far and who signs off. |
| - | Done | The four lines' names are fixed in code (`plan/work-templates.ts`, `LINE_NAMES`) and written as `<h3>` headings, so they can be found in a description later; the studies' earlier names (Target, Change, Control, Boundary) are read as the same lines, never written. Everything else is the team's data: request types (name, what it means, a hint and an example per line, typical stories), the generic hints for no type, why each line matters, and four choice lists (Environment, Touches, Done when it is, Not without asking). Seeded with 14 types. |
| - | Done | Every line is optional and nothing ever blocks: a title-only create sends and writes exactly what QC-1 did (the e2e checks the preview has no Tags and no headings). A type brings its hints as the grey text in each box; its example shows under the box only while that line has focus (mouse or keyboard), and the box names it for a screen reader. The ? beside each name says why it matters (hover, focus or click). See a full example opens beside the form and copies nothing into it. |
| - | Done | Showing or hiding an example waits until a press is released (`ui/FourLines.tsx`), so the click that moved focus lands on the control it started on; without it, clicking Environment moved the button down by the example's height mid-click and the click was lost. Keyboard focus shows at once. |
| - | Done | At create only (`new_item`): the four lines into the description under their headings (after anything typed in Description), How we'll check plus "Checked by: <who>." into the acceptance criteria when the type has the field (else the preview says it's only in the description), and one tag `type:<tag>` in System.Tags. Nothing else: no AI request, no rewrite of an existing item's description, tags or acceptance. Preview, confirm, read back, audit log, undo and the GD-2 check on the text are unchanged. |
| - | Done | A tag is set once from a type's first name (lower case, hyphens, never `;`, `,` or `@`) and never changes: renaming keeps it, and removing only takes the type off the form, so items and drafts that carry it still show its name. |
| - | Done | When the project refuses the tag (adding a new tag needs the project's Create tag definition permission; Microsoft doesn't document the error text, so a 400 that names tags, on a create that carries a `type:` tag, counts; a 403 keeps its own message, since it can be about the area or the parent), nothing is created and the preview says so with one button, Create it without the tag (the same create with `noTag`). Never automatic. The demo's Harbor refuses new tags so this path can be seen. |
| - | Done | Choices instead of typing where the answer comes from a short list: Environment (one), Touches (any), Checked by and Signed off by (a person on the client's DevOps project from the same read as Assigned to, never another client's people, or a role typed in), Done when it is (one), Not without asking (any); each with Other. People's emails are kept only to check them; the description names them. |
| - | Done | Readiness: the card shows the four lines as one block above the rest of the description, the request type, and a quiet chip, Ready or "Missing: <lines>". How far and who signs off counts once Done when it is is chosen (built, in test, published and approved are different things); an item written under the earlier names counts its text. |
| - | Done | Drafts keep the type and the lines (`draft_stories.brief`, JSON; export schema 40): Save as draft, the draft editor (`draft.update` takes `brief`) and a draft's Create in DevOps all carry them. A type removed after the draft was saved stays with the draft. |
| - | Done | Admin › Work templates (`templates.load` for everyone, `templates.save` for FocusTime admins only, the one `isAdmin()` check): the list of types with counts, the editor, and the New form as people will see it beside it with the unsaved edits. One Save with one line of why; each change audited in Admin › Audit (area `work_templates`: what, before, after, why, who, when). A save made from an older version is refused (409) with Reload theirs, never merged. Settings › Today and Week shows the templates read-only, "Set by your FocusTime admin". |
| - | Done | Counts per type for admins: items created with it and how many had all four lines (`work_template_uses`, an app table: tag, time, complete). Counts only, never who, which client or which item. |
| - | Done | Phone: the four lines under More, one per row, the request type in the main form. 1440 × 900: with a type chosen the form fits without scrolling (the dialog sits higher and widens to 820 px; the full example widens it beside). Ctrl+Enter anywhere in the form opens the preview (or saves the draft without a write PAT); Escape as before. |
| - | Done | In the Guide: "Writing work a builder can use" (four things you do, four questions, one full example). |
| - | Done | Checked by and Signed off by are checked on the server like Assigned to: a person must be on the client's DevOps project (a role typed in is just words), and changing the client in the New form or the draft editor drops people chosen from the old one. The earlier names (Target, Change, Control, Boundary) count only when at least two head lines, since alone they are everyday words. A choice can't hold a comma or semicolon. |
| - | Done | Review 1 (a consultant creating three items, screenshots and the why only). Fixed: hints read as answers (now lighter and italic), a chosen chip had no mark (now a ✓), the ? covered the field below (now opens above), the Missing chip was easy to miss (now amber), a missing period in the tag refusal, and three screenshots (the form shot before its level switch, the keyboard shot with focus on the ? rather than the box, Settings under the first-launch welcome). Kept, as the step asked: the lines appear with a type or Add the four lines; on the phone they sit under More; the line names are fixed. Hints' length and wording are the team's to edit in Admin. |
| - | Done | Review 2 (the diff against the risks). Fixed: people chosen for another client carried over on a client change and weren't checked on the server; any 403 on a tagged create read as a tag refusal; a lone "Target" or "Change" line was read as the four lines; a long type name could make a numbered tag that failed the pattern (so it would never be written); a choice with a comma made a save that changed nothing; Ctrl+Enter in a chip's Other box dropped what was typed; Other's box cleared when its text matched a choice; the menu offered the admin save to everyone (the server already refused). Left as an open question: the tag isn't in the GD-2 exit check. |
