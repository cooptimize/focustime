## RB-5: SQL objects by schema or by type (Nov 14)

Unnumbered until merge.

| # | Status | Decision |
|---|---|---|
| - | Done | Why: the product owner opened a client's warehouse in By kind and got hundreds of objects as one list sorted by name, and asked to see them by schema or by object type: grouped by schema, then in folders by type; grouped by type, then by schema. A warehouse is organized that way and so are the people who work in one ("the dim tables", "the procedures in staging"). |
| - | Done | Names only, as RB-2 and RB-4 decided. An object's type and schema come from the folders in its path (`plan/code-kinds.ts`). No file is opened to group anything and no new request goes to DevOps: By kind makes the same reads as before, and changing the grouping asks FocusTime's server only to remember the choice. Who may read, what is kept and what is logged are unchanged; `actions/code-actions.ts` is untouched. |
| - | Done | STEP 0.3, the layout, checked against the documentation on Nov 14. A Fabric warehouse and a Fabric SQL database are kept in Git as a SQL project inside the item's folder, and "defaults to organizing the project files by schema and object type. For example, a table named `Table1` in the `dbo` schema would be represented by a file path of `dbo/Tables/Table1.sql`" ([warehouse definition](https://learn.microsoft.com/en-us/rest/api/fabric/articles/item-management/definitions/warehouse-definition), [SQL database definition](https://learn.microsoft.com/en-us/rest/api/fabric/articles/item-management/definitions/sql-database-definition), [SQL database source control](https://learn.microsoft.com/en-us/fabric/database/sql/source-control): "a file named `MyTable.sql` in the folder `dbo/Tables`"). The item's folder is `<name>.<type>` with `.platform` ([Git source code format](https://learn.microsoft.com/en-us/fabric/cicd/git-integration/source-code-format)). The project tree shows `Functions`, `Tables` and `Views` under a schema's folder ([Develop warehouse projects](https://learn.microsoft.com/en-us/fabric/data-warehouse/develop-warehouse-project), which recommends "Schema/Object Type"); `StoredProcedures` is named as a subfolder in [Database DevOps in SSMS](https://learn.microsoft.com/en-us/ssms/database-devops). The definition also names a shared queries folder (`.sharedqueries/*.sql`, left out of the build) and the project file (`sqldw.sqlproj`, `sqldb.sqlproj`). A SQL database project outside Fabric may be laid out by schema and type, by schema, by type, flat or as one file ([SqlPackage extract](https://learn.microsoft.com/en-us/sql/tools/sqlpackage/sqlpackage-extract), `ExtractTarget`); the pages give no folder names for those. |
| - | Done | The type rules built from that. Inside a database (a warehouse item, a SQL database item, or a folder holding a `.sqlproj` and everything under it), a `.sql` file's type is the folder it sits in: Tables, Views, StoredProcedures (and the spellings RB-2 already read: Stored Procedures, Procedures, Sprocs), Functions; the folder above is its schema. A file in the database's shared queries folder is a Shared query. The project file is a SQL project. Any other `.sql` file is a Script. Outside a database the type is read the same way and no schema is said (RB-4's rule). |
| - | Done | A schema's own definition is a Schema, not a script. The documentation names no folder for it, or for roles and users (the warehouse page says security isn't kept in the project by default). The extract tool writes them to a `Security` folder at the top of the database, so that folder is read: a file there with the name of one of the database's schemas (a folder above an object folder) is that Schema and sits in its schema; any other file there is a Security object with no schema. This one rule rests on what the tool writes, not on a sentence of the documentation (open question). |
| - | Done | One switch, Group by Schema · Type, wherever SQL objects are listed in By kind: inside an opened warehouse or SQL database, and in the SQL group (which is where a SQL project's objects are). Schema: schema folders, each holding type folders, each holding objects. Type: the other way round. It starts on Schema, is the person's own (`[ui] code_sql_group`, saved the way Day's timeline switch is, by `ui.set_code_sql_group`), and is one choice everywhere it shows. A demo session's choice stays in that demo session's memory. |
| - | Done | Order: Tables, Views, Stored procedures, Functions, then the other types by name (Schemas, Security, Shared queries, SQL projects), then Scripts. Schemas by name ignoring case (two spellings of one schema are one folder), then "No schema" for an object whose path shows none. |
| - | Done | A folder shows its count; an empty folder never shows; every object is in exactly one folder and the counts add up to the list's total (tests). Folders start closed, except a folder that is the only one at its level. A folder with more than 100 objects shows 100 and "Show all 150". Expand all and Collapse all work on one tree. |
| - | Done | The SQL group: with more than one database in the client, the first level is the database ("Gold warehouse", "Warehouse SQL project"), by name, with the repo beside it where the client has more than one repo, and "Not in a database" last for loose SQL files. With one database or none the grouping starts at the top. Decided from all the client's SQL things, not from what the filter leaves. |
| - | Done | An object's row is its mark and its name and opens its file (Show in files is on the file, as before). It doesn't repeat its folders: under dim › Tables it is "Store". Only a file in no database says where it is ("In /scripts"). |

Clearing it puts the tree back as it was. A database's tree is narrowed even when its item was opened by hand (a model still shows all its tables then, as before). |
