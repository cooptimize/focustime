## VM-5: A Stop before the day no longer cancels the morning's automatic start (Nov 18)

Unnumbered until merge.

| # | Status | Decision |
|---|---|---|
| - | Done | What happened on Nov 18: the product owner worked past midnight and stopped his VM at 2:51 AM; at 9 it was still off. VM-2's review had added one rule, "a Stop I press today also skips today's automatic start" (`vm.confirm` in `actions/vm-actions.ts` added today to the skipped days), and 2:51 AM is already today, so the morning's start was skipped. Settings then said "Skipped today" with no reason, though he never pressed Skip. Confirmed in the code with a failing test first (a Stop at 2:51 AM, then the tick at the planned time: `not_due`, no start). Nothing was read from Azure or production for this step. |
| - | Done | The rule (`stopEndsToday`, `plan/vm-autostart.ts`): a Stop confirmed before today's planned time (the day's start less my minutes, in my own time zone) doesn't skip today's start. One at or after it ends today's start as before, so a VM stopped during my day is never started again by FocusTime that day, also while a start is still being retried after an unreadable state (VM-4; the next pass settles it as skipped). A day with no planned time (no working hours) is skipped as before: there is no start to keep. Tested a minute before, at and after the time, and across midnight in Tokyo (east of the server's UTC) and Los Angeles (west). From the review pass: working hours that start at midnight put tomorrow's planned time the evening before, so a Stop after it ends tomorrow's start too (`stopEndsDays`); a VM stopped at 11:50 PM is never started at 12:00 AM. |
| - | Done | The Stop's preview: while today's start is still to come (on, production, a chosen day with working hours, not PTO or a holiday, not paused, skipped or tried already, its time ahead; the same answer as the "Next:" line, read as if the VM were off), one line, "It will start again today at 8:55 AM.", and one box under it, "Skip today's start too", unticked. Ticked, `vm.confirm`'s `skipToday` skips today as Skip this one does. With no start to come the preview is as it was. After such a Stop the message says "Stopped. It will start again at 8:55 AM." |
| - | Done | A skip says why: each skipped day keeps how (`skipHow`: skip, not_today or stop) beside `skipped`, in the same per-person state row (`vm_autostart`), so no migration; an older build reads the state and drops the reasons. Settings' My VM line and the chip's menu say "Skipped today: you pressed Skip this one", "Skipped today: you chose Not today on Day" or "Skipped today: you skipped it when you stopped the VM", before the planned time too (it said "Wed is skipped." then). A skip kept before VM-5 says only "Skipped today". A day skipped twice keeps its first reason. |
| - | Done | Don't skip (`vm.autostart_unskip`, the one new action): in the chip's menu and beside Settings' line while today's planned time is still ahead; it takes back today's skip only, in the signed-in person's own plan, reads nothing from Azure, and is refused at and after the time (the way on is Start, as before). |
| - | Done | Unchanged: when the start runs, on which days, the retries, what is read from Azure, the Azure client's allowed calls, once a day, production only (the background policy and its test are untouched), Skip this one and Not today. CLAUDE.md's Azure hard rule has no sentence saying a Stop skips the day, so it is unchanged. No migration, dependency or background work. |
| - | Done | The first download: the chip's menu, which loads with the first screen, carries today's skip with its reason and Don't skip, and the Stop's preview its line and box. Trimmed first (the message after a Stop comes from the server with the preview's words; the new action's registry entry is short). Before WK-6 merged this needed the limit at 348.7 kB; main's limit since WK-6 (361 kB) covers it, so the record is main's. |
